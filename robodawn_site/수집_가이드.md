# RoboDawn 결과 사이트 수집 가이드

robodawn.top/results의 RoboTwin 2.0 기록을 브라우저로 직접 보며 옮겨 적기 위한 문서다. 사이트는 자동 접근을 막고 있으므로 사람이 화면을 넘기며 수집한다.

## 왜 모으나

| 목적 | 필요한 것 | 단계 |
|---|---|---|
| 베이스라인 재현 검증: 우리 하네스로 돌린 결과가 원 실험과 맞는지 | 과제별 성공 수, 에피소드별 seed, 턴 수, 성공 여부 | 1 |
| 재현 조건 확인: 같은 요청을 보내고 있는지, 추론이 켜져 있었는지, 비용이 얼마인지 | 한 턴의 전체 프롬프트, 응답, 토큰 사용량, 실행 피드백 | 2 |
| 연구 근거: Flash가 어디서 실패하는지, Clef 정렬이 끼어들 자리가 있는지 | 실패 에피소드의 턴별 기록과 이미지 | 3 |

**1단계만 끝나도 재현을 시작할 수 있다.** 2단계는 첫 재현 실행과 나란히 진행하고, 3단계는 재현이 맞은 뒤에 한다.

## 사이트 구조

- 상단 탭: **Overview / Demonstrations / Episodes**. 수집은 전부 **Episodes** 탭에서 한다. 왼쪽 위 벤치마크 선택은 **RoboTwin 2.0**이다(RoboDojo가 아님).
- 왼쪽: 과제 목록(50개)과 각 과제의 `성공 수/10`. 아래로 스크롤해야 26번째 과제부터 보인다.
- 오른쪽: 과제를 고르면 에피소드 카드 10개가 나온다. 카드마다 `Episode k`, `seed`, `턴 수`, `Success/Failure`.
- 카드를 고르면 아래에 리플레이가 열린다.
  - 제목 아래 캡션: `Gemini 3.8 Flash · RoboTwin 2.0 · seed … · demonstration entry N · M turns`
  - 턴 슬라이더(`turn k / M`). 빨간 턴은 실패한 명령이 있는 턴이다.
  - 턴별 관측 이미지: Head camera(크게), Top camera, Left wrist, Right wrist
  - 손끝 좌표: `Left fingertips x / y / z cm`, `Right fingertips …`
  - Agent trace: 그 턴의 장면 설명, 진행 상황, 계획, `execute({commands: [...]})`, 명령별 완료/실패
  - **Inspect the prompt, reply and execution of this turn**: 펼치면 그 턴의 전체 프롬프트와 응답
  - **All turns in this episode**: 턴별 명령과 결과 한 줄 요약
  - **System prompt of this episode**: 시스템 프롬프트 전문
- 리플레이 시간(0:14 등)은 초당 300토큰을 가정한 연출이다. 실제 지연 시간이 아니므로 적지 않는다.

## 1단계: 과제와 에피소드 결과 (필수)

**파일:** [`tasks.csv`](tasks.csv), [`episodes.csv`](episodes.csv). 이미 만들어 두었다.

### tasks.csv

과제 50개가 줄마다 있다. 앞 25개는 받은 PDF에서 채웠다. **나머지 25개의 `success`만 채우면 된다.**

| 열 | 내용 |
|---|---|
| task | 저장소 과제 이름(밑줄) |
| site_name | 사이트 표기(공백) |
| success | 성공 수(0~10) |
| episodes | 에피소드 수(10이 아니면 그대로 적는다) |
| note | 특이사항 |

### episodes.csv

500줄(과제 50 × 에피소드 10)이고, `expected_seed`에 저장소 `harness/valid_seeds/`의 앞 10개 seed를 미리 넣어 두었다. adjust_bottle은 PDF에서 채웠다. 과제마다 카드 10개를 보며 채운다.

| 열 | 내용 | 어디서 |
|---|---|---|
| seed | 카드의 seed | 에피소드 카드 |
| turns | 카드의 턴 수 | 에피소드 카드 |
| outcome | `success` / `failure` | 에피소드 카드 |
| demo_entry | `demonstration entry N`의 N | 카드를 열면 나오는 캡션 |
| note | 아래 경우에 적는다 | |

- `seed`가 `expected_seed`와 다르면 그대로 적고 note에 `seed 불일치`라고 쓴다. 이 경우가 가장 중요하다. 우리 재현이 다른 씬을 돌리게 되기 때문이다.
- `demo_entry`는 카드를 하나씩 열어야 보인다. 시간이 부족하면 과제마다 에피소드 0 하나만 열어서 적고, 나머지는 비워 둔다. 시연 폴더 `<task>`(entry 1)와 `<task>+2`(entry 2) 중 어느 쪽이 들어갔는지 확인하는 데 쓴다.
- 턴 수가 45 미만인 실패는 note에 리플레이 마지막 줄의 종료 문구(예: `Episode ended · …`)를 적는다. 모델이 done을 반복했는지, 응답 실패인지 등을 가려낸다.

### 1단계 점검

다 채운 뒤 아래가 맞는지 본다. 틀리면 해당 과제를 다시 확인한다.

- `tasks.csv`의 success 합계가 **311**이다. 앞 25개 합이 152이므로 나머지 25개 합은 **159**여야 한다.
- 과제마다 `episodes.csv`의 success 수가 `tasks.csv`의 값과 같다.
- 턴 수는 1~45다. 45인 에피소드는 거의 모두 failure여야 한다.

## 2단계: 재현 조건 확인 (Inspect)

**대상:** 아래 3개 에피소드. 과제마다 할 필요 없다.

| 에피소드 | 이유 |
|---|---|
| `adjust_bottle` 에피소드 0 (성공, 10턴) | 짧은 성공 기준 사례 |
| `adjust_bottle` 에피소드 3 (실패, 21턴) | 45턴 전에 끝난 실패 |
| 1단계에서 빨간 턴(실패 명령)이 보인 아무 에피소드 하나 | 실패 피드백 문구 |

**턴 선택:** 각 에피소드의 **턴 1, 중간 턴 하나, 마지막 턴**.

**저장 형식:** `inspect/<task>__ep<k>__turn<t>.md` 파일 하나에 Inspect를 펼쳐 나온 내용을 **전부 그대로 붙여 넣는다.** 요약하거나 줄이지 않는다. 문자 단위로 우리 요청과 비교한다.

특히 아래 항목이 있는지 보고, 있으면 꼭 들어가게 한다.

- [ ] **토큰 사용량.** prompt, completion, **reasoning** 토큰. 가장 중요하다. 원 실험에서 추론이 실제로 켜져 있었는지(수백~수천이어야 한다)와 에피소드당 비용을 추정하는 근거다.
- [ ] 지연 시간, 재시도 횟수(표시된다면)
- [ ] 사용자 메시지 본문: 로봇 상태 문자열, 지난 턴 피드백, 기억(scratchpad), 이전 턴 요약
- [ ] 모델 응답 원문(JSON). scene, progress, plan, commands 등 키 이름과 순서
- [ ] 실행 결과 문구. 명령별 성공/실패 메시지, 실패 이유
- [ ] 이미지가 몇 장, 어떤 순서로 들어갔는지(시연 프레임 포함 여부)

**시스템 프롬프트:** 에피소드 하나에서 `System prompt of this episode` 전문을 `inspect/system_prompt.md`로 저장한다. 과제마다 바뀌는 부분이 있는지 보려면 성격이 다른 과제(예: `handover_block`) 하나에서도 저장한다.

## 3단계: 실패 사례 턴별 기록 (재현이 맞은 뒤)

**대상:** 성공률이 낮은 과제의 실패 에피소드. 먼저 아래에서 과제마다 2개씩(45턴을 다 쓴 실패 1개, 일찍 끝난 실패 1개) 고른다. 나머지 25개 과제에서 0~3/10인 과제가 나오면 추가한다.

| 과제 | 성공 |
|---|---|
| lift_pot | 0/10 |
| pick_diverse_bottles | 0/10 |
| hanging_mug | 1/10 |
| pick_dual_bottles | 1/10 |
| handover_block | 2/10 |
| move_pillbottle_pad | 3/10 |
| open_laptop | 3/10 |

비교용으로 성공률이 높은 과제의 성공 에피소드 2~3개도 같은 형식으로 받는다(예: `click_bell`, `grab_roller`).

**저장 형식:** 에피소드마다 `turns/<task>__ep<k>.csv` 하나. 한 턴이 한 줄이다.

| 열 | 내용 |
|---|---|
| turn | 턴 번호 |
| left_tip | 왼손끝 `x/y/z` (cm, 화면 표기 그대로) |
| right_tip | 오른손끝 `x/y/z` |
| scene | 장면 설명(모델 문장) |
| progress | 진행 상황(모델 문장) |
| plan | 계획(모델 문장) |
| commands | 명령들, `;`로 구분 |
| result | `completed` / 실패 문구 |
| red | 빨간 턴이면 1 |

`All turns in this episode`를 펼치면 commands와 result를 한 번에 옮길 수 있다. 나머지는 턴 슬라이더를 넘기며 채운다.

**이미지(선택, 시간이 있으면):** 위 에피소드 중 3~4개만, 턴마다 Top camera, Left wrist, Right wrist를 `images/<task>__ep<k>/turn<t>_{top,left,right}.png`로 저장한다. Head camera는 녹화 영상 프레임이라 모델 입력과 다를 수 있다. 우리 Clef 오프라인 시험을 domain-randomized 씬에서 다시 돌리는 데 쓴다.

**실패 원인 메모(선택):** 에피소드마다 한 줄로 `turns/<task>__ep<k>.csv` 맨 아래 note에 적는다. 예: "병 위치까지는 왔는데 y축으로 계속 2~3 cm 어긋나서 못 잡음", "잡은 뒤 들다가 놓침", "계획부터 잘못됨". 정렬 실패와 계획 실패를 나누는 게 목적이다.

## 수집하지 않는 것

- **Demonstrations 탭.** 시연은 저장소 `demos/robotwin2/`에 이미 있다.
- **RoboDojo 탭.** 이번 연구 범위가 아니다.
- **리플레이 시간 표시.** 연출이다.
- **Overview 탭.** README와 논문 숫자가 같다.

## 폴더 구성

```
robodawn_site/
├── 수집_가이드.md          이 문서
├── tasks.csv               1단계 (50줄, 앞 25개 채움)
├── episodes.csv            1단계 (500줄, adjust_bottle 채움)
├── inspect/                2단계
│   ├── system_prompt.md
│   └── <task>__ep<k>__turn<t>.md
├── turns/                  3단계
│   └── <task>__ep<k>.csv
└── images/                 3단계 (선택)
    └── <task>__ep<k>/turn<t>_{top,left,right}.png
```

화면에서 애매한 것은 스크린샷이나 PDF로 함께 넣어 두면 된다. 받은 뒤 점검과 표 정리는 이쪽에서 한다.
